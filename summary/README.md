# fixed_imb_s512 resctrl 比較レポート

## 簡潔なまとめ

`resctrl` は、節目の100ステップごとの OMPT サンプルではほぼ遅い。一方で、節目と節目のあいだの進行は、実行長によって速く出る場合と遅く出る場合がある。

- 500 step: 全体はほぼ同じだが `resctrl` がわずかに速い。節目の `heat_update` は遅いが、200-500 の節目間で取り返している。
- 700 step: `resctrl` が約0.78秒速いが、差は0.62%で小さい。2000 step 実行時の前半ほどの大きな先行は再現していない。
- 1000 step: `resctrl` が遅い。節目も節目間も全体的に遅く、制御メリットより制限コストが勝っている。
- 2000 step: `resctrl` が少し速い。前半で大きく先行し、後半でかなり失うが、最後に少しリードが残る。

性能改善としてはまだ薄く、実行時間差は最大でも 1% 未満。いまのMBA制御は、性能を安定して上げるというより、電力とエネルギーを下げながら、ケースによって少し速くなることがある、という状態に見える。

## どこで効いて、どこで悪化するか

500 step では、100-200 は遅いが、200-500 は連続して速い。つまり短い実行でも「節目は遅いが、節目間で回収する」構図は見える。ただし総差は -0.123 s で小さい。

1000 step では、100-1000 のすべての節目間で `resctrl` が遅い。これは仮説と逆で、MBA制限による遅延が支配的。

2000 step では、100-700 で大きく速い。700-1000 は遅く、1000-1200 で少し回復し、1200-1800 で大きく失う。最後は小さく揺れる。結果として全体では -0.466 s だけ速い。

## 700 step で「2000 step 前半の速さ」はどこに行ったか

今回の700 step実行でも `resctrl` は速いが、2000 step実行時に見えていた前半の大きな先行はかなり縮んでいる。`heat_update` の開始時刻差で同じ 100-700 を比べると、2000 step実行時は -1714.408 ms、今回700 step実行は -548.650 ms。差し引きで約 1.166 秒ぶん、見かけの先行が小さくなった。

| 区間 | 2000 step実行時 | 今回700 step実行 | 変化 |
|---:|---:|---:|---:|
| 100-200 | -193 ms | +141 ms | +334 ms |
| 200-300 | -350 ms | -89 ms | +261 ms |
| 300-400 | -449 ms | -218 ms | +231 ms |
| 400-500 | -403 ms | -152 ms | +252 ms |
| 500-600 | -227 ms | -151 ms | +76 ms |
| 600-700 | -91 ms | -80 ms | +12 ms |

一番大きい違いは 100-500。2000 step実行時は 100-500 だけで約 -1.396 秒の先行があったが、今回700 stepでは約 -0.166 秒しかない。つまり「なくなった速さ」の大半は、序盤100-500の区間差が再現しなかったことによる。

この差は、アルゴリズム上の必然というより実行間の状態差を強く含んでいる可能性が高い。今回も `target 100%` のスレッドは平均 -2.399 ms 速い一方、`target 30%` のスレッドは平均 +65.127 ms 遅い。MBA制御は速いスレッドを少し助けるが、制限されたスレッドをかなり遅くするため、どのスレッドがその時点の律速になるか、OS配置、メモリ状態、温度/周波数、前段の進行差で結果が振れやすい。

したがって、700 stepの結果は「節目以外なら必ず速い」というより、「200-700では速い傾向は残っているが、2000 step実行時の序盤ほど強い効果は再現していない」と読むのが安全。

## スレッド別の見え方

共通して、MBAは全スレッドを速くしているわけではない。`30-60%` に絞ったスレッドは大きく遅くなり、`100%` のまま残したスレッドが少し速くなる。

### 500 steps

- `100% MB` のスレッド平均差: -2.275 ms
- 制限されたスレッド平均差: +59.835 ms
- 速い側: t6 -5.128 ms, t11 -3.949 ms, t10 -3.586 ms
- 遅い側: t13 +74.275 ms, t14 +73.329 ms, t12 +72.596 ms

### 2000 steps

- `100% MB` のスレッド平均差: -3.923 ms
- 制限されたスレッド平均差: +39.703 ms
- 速い側: t6 -5.795 ms, t10 -5.353 ms, t9 -4.918 ms
- 遅い側: t15 +45.357 ms, t14 +41.888 ms, t13 +41.482 ms

1000 step は raw OMPT が後続実行で上書きされているため、スレッド別の再集計はこのレポートでは省略している。ただし領域サマリでは `heat_update` の max thread はほぼ改善せず、mean thread が +25.94 ms 増えており、制限コストが勝ったと見てよい。

## なぜこうなるか

考え方は次の通り。

1. 節目ステップでは、resctrl適用、PMU計測、CSV出力がまとまって走るため、`resctrl` は遅くなりやすい。
2. 節目以外では、前回のMBA設定が残るため、追加のresctrl書き込みなしで帯域配分だけが効く。ここで `100% MB` のスレッドが軽くなれば、節目間の進行が速くなる。
3. ただし制限されたスレッドは大きく遅くなる。メッシュが軽くなる、インバランスが減る、または制限対象がその時点の律速に合わなくなると、制限コストがメリットを上回る。
4. そのため、500 step と 2000 step では少し勝つが、1000 step では負ける。効果は実行長や時系列の状態にかなり敏感。

## いまの結論

現状の制御は、性能最適化としてはまだ強すぎる可能性がある。特に `30-40%` まで絞るスレッドが大きく遅くなり、節目サンプルではほぼ毎回悪化している。

次に見るなら、まず `min MBA` を上げる、または `target` を保守的にして、`30-40%` まで落とさない設定を試すのがよい。狙いは、`100% MB` 側の小さな改善を残しつつ、制限側の +40ms 以上の悪化を抑えること。
